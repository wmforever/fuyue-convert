# 后置金额符号：保留来源差异并提示冲突

生产起点 `841bc848844458fba909f3d015743cf891ab28b8` 存在已复现的遗漏：同位置 `Amount 048.65-` 与 `Amount 048.65` 被当作重复，数字比较没有后置负号，且文字归一化删掉符号；没有冲突提示。此问题在本轮修复前已经存在，**不是缩放批次的新回归**。本轮结束后的缩放/可见性试验均未重跑。

## 冻结复现与修复范围

在改动生产源码前冻结 **30 组 Java 对照、12 个独立 OFD**。六个后置 ASCII/Unicode 正负号场景包括普通空格、NBSP 和 U+2212；另有美元金额、会计括号、紧邻/带空格范围、列表文字和独立负数字段。每个 OFD 有一条确实新颖的扫描页脚，避免“没有新文字”错误阻止进入成功下载路径。源图 2550×3300、300DPI，Liberation Sans 56px，源 OFD/PNG、生成器、字体和真值均 SHA 绑定；不会挑选识别结果改变真值。全角正负号、单位、前导零、不同符号原文和跨行分隔符另由真实 Java 包内方法验证。

修复前 30 组 Java 实际调用证明后置正负号被忽略。**12 次带认证 HTTP→独立 JVM→实际下载全部成功**，其中 **7 个金额差异的 OCR 层被静默删除、没有冲突提示**。会计括号案例在旧逻辑中已经保留两层并提示冲突；四个范围/列表/分字段控制也没有此遗漏。

最小改动只扩充数字字面量比较：既有五个符号 `+ - − － ＋` 可以作为数字字段末尾的后置符号，其后只能有空白和既有的闭括号、货币或单位后缀。数字到符号之间不能跨逻辑行；符号后还有数字、范围/列表/字段文字时，保留原有处理。**不修改 `NUMBER` 核心正则，不解释范围为负金额，不合并不同数字，不重写原文，也不按置信度选择其中一个来源。** 模糊的非末尾符号仍不推广识别。

例如修复后真实下载为 `Amount 048.65Amount 048.65-`，并返回 `OCR_RECOGNITION_CONFLICT`。两种来源按已有几何顺序拼接，供人工复核；这不是新的财务规范化输出。既有 `048.65-049.65` 范围字面量、`048.65 - 049.65` 的原有两个数字标记、`048.65 - NOTE` 列表分隔符和 `048.65 | -049.65` 独立负数字段保持原处理。反射查看实际私有数字方法的 token，防止仅凭正向下载成功漏掉错误的范围分类。
